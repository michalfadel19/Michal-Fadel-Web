Playwright and TypeScript: UI and API testing

Last updatedOctober 2026

1. Objective

To practice building reliable, maintainable automated tests that cover both what a user sees (UI) and what happens underneath (API), and to run them automatically in a CI pipeline on every change.

2. Scope

  • In scope: UI tests for login, the shopping cart, and checkout; API tests for the posts endpoints (GET, POST, PUT, DELETE), including negative cases.
  • Out of scope: performance, load, security, and cross-browser testing.

3. Approach

  • Page Object Model: each page has its own class holding its locators and actions, so a change to a page is fixed in one place and the tests stay short and readable.
  • Independent tests: every test starts from a clean state and uses synthetic data, so tests can run in parallel without affecting each other.
  • Positive and negative coverage: valid flows plus invalid input, missing fields, blocked access, and a non-existent resource.
  • Test plan: a test plan in the repository lists the scope, approach, and every test case, and the test case IDs match the test names in the code.
  • CI/CD: a GitHub Actions workflow runs the full suite on every push and saves the HTML report.

4. Test environment

  • Browser: Chromium, run by Playwright
  • Runs: locally (Windows, VS Code) and in GitHub Actions (Ubuntu)
  • Test data: synthetic only; no real personal data is used

6. Issues and resolutions

  • Browser not installed (environment issue): on the first local run, all UI tests failed because the Playwright browser had not been downloaded. This was a setup problem, not a product defect. Installing the browser fixed it, and the tests then passed.
  • Product defects: none found. Both targets are public practice sites.

8. How I worked on it

I started from an AI-generated scaffold, then ran it, fixed the setup, read through the page objects and tests to understand how they work, and extended it myself. For example, I wrote TC-LOGIN-06 (blocked direct access without logging in) and added it to the test plan. I use AI tools the same way in my QA work: to speed up the first draft, then review and verify the output.

9. Ongoing work

This framework serves as a living repository. I am continuously expanding coverage parameters, writing additional edge-case checks, maintaining code parity, and ensuring execution results remain explicitly updated. The GitHub repository will always reflect the most recent updates and changes I make.

10. Notes and limitations

  • Both targets are public practice sites, so this shows testing technique, not production experience.
  • JSONPlaceholder does not save what is sent to it, so the create, update, and delete tests verify the response, not stored data.
